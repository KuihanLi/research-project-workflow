# Research Project Workflow

> 中文说明 | [English](README.md)

面向长期科研项目的轻量级 ChatGPT Skill，覆盖**研究 IDEA 生成与演化、多研究分支并行、代码与受控实验、证据解释、论文写作及可恢复交接**。从单线的“IDEA → 方法 → 实验 → 论文”扩展为**多头探索 + 可版本化创新点 + 统一证据约束**；仍然坚持 Completion first，不让流程成为交付阻碍。

## 新版的核心变化

### 1. IDEA 不再是不可改变的单一路线

同一研究任务可同时保持原始 IDEA、互斥假设、补充机制、低成本强基线、异常专项以及现实部署条件下的约束性方案。它们共享有效的实验与数据，但拥有各自的可证伪预测。分支可以推进、缩小边界、变更机制、合并、暂停或终止。不是同时跑完所有 IDEA，也不要求每个分支单独维护重复的实验。

### 2. 从旧实验结果反向生成候选创新

新增三个可以并行的研究方向：

| 研究线 | 从什么发现问题 | 走向什么研究 |
| --- | --- | --- |
| A. 效应异质性 | 任务、来源、特征、容量或指标上的增益/退化反转 | 条件使用信息、稳健表征、低成本机制 |
| B. 异常机制 | 具有结构的错误指纹而非一个坏均值 | 至少两个竞争解释及最小区别性对照 |
| C. 显式约束 | 一个方法在部分现实可识别条件中更好 | 定义目标域、覆盖度、风险、资源和域外策略 |

这些是**发现假设的途径**，不是算法原创性的证明。必须继续验证可执行技术差异、强简单/已有算法基线、公平条件和决定性实验。

### 3. 创新点可以变更，但不能擦除证据历史

每个实质创新点维护可追溯的 `idea_id / claim_version / parent_id / evidence_ids`。当新实验否定旧假设时，可以有依据地开出子分支或改变主要贡献，并保留原始负结果。**看过 final test 后才选中的 IDEA、指标、任务或适用域，不允许用同一测试结果冒充新主张的独立确认**。更名、换分支、重新冻结均不重置测试集的使用历史。

### 4. 并行而不失控

共享同一个真实数据划分、强基线和实验账本。优先投向最便宜且能排除竞争解释的实验，低成本淘汰弱方向，把独立确认资源留给真正有希望的候选；对合并方案做 A/B/A+B/强简单基线对照，而不是看到模块堆叠就宣称互补。

### 5. 仍然保护科研结论

- 训练/验证用于调参与分支选择；独立最终测试只用于冻结后的确认。
- 报告真实统计独立单位与配对效应；不能把重复窗口和重复来源视为独立样本。
- 将相关、机制消融、受控干预和因果结论分层表达。
- 受限条件的整体收益要给出**可部署的条件判定、覆盖率、主指标、失败组风险、成本和域外边界**，不是“挑出有利样本后全部获胜”。
- 在昂贵主实验冻结前进行新/改 claim 的针对性查新与强 baseline 可运行性核验。
- 保留科学负结果和工程故障的区别，不承诺不存在的实验执行。

## 使用入口

在 ChatGPT 对话中可以直接使用以下请求，不必按固定顺序：

```text
使用 Research Project Workflow，结合现有实验结果并行提出 3 条具备可区分预测的 IDEA 分支，按最小实验成本安排先后，明确每条的淘汰条件。
```

```text
原 IDEA 已出现某任务增益、某来源严重退化，请从异质性、异常机制、显式部署边界三个方向反向挖掘新创新，保留强简单基线和 negative evidence。
```

```text
对比当前 IDEA-A、IDEA-B 的证据等级与独立性，判断应继续、合并、缩小条件域还是终止，并更新创新点版本但不要重跑已完成任务。
```

```text
根据已冻结的候选创新点与证据约束，形成能够支持投稿的贡献叙事，指出仅属于探索发现而不能作为独立确认的主张。
```

新会话可从 `HANDOFF.md` 和项目的 `IDEA_REGISTER.md`（如存在）恢复，避免重新发明已经证伪的 IDEA。

## 结构与加载

```text
research-project-workflow/
├── SKILL.md                             # 会话级轻量核心
├── references/
│   ├── idea-portfolio-and-reverse-innovation.md  # 新增：并行、二次创新、边界
│   ├── idea-to-plan.md                  # 分支级研究计划、查新、baseline、冻结
│   ├── code-experiment-loop.md          # 运行与分支实验对照
│   ├── paper-workflow.md               # 论文与 claim 证据
│   ├── context-management.md           # 多分支状态恢复
│   └── handoff-workspace.md            # 最小恢复交接
├── scripts/package_handoff.py          # 原有恢复包打包工具
├── agents/openai.yaml
└── assets/icon.svg
```

`SKILL.md` 会话内读取一次；按任务只选最相关的 `references/`，不要每次完整加载。项目状态放在项目工作区；只有多个活跃分支确有需要时才维护简短的 `IDEA_REGISTER.md`，不强制建立额外模板。论文工作、投递、交接延续旧版规则；重大修订、显式请求或可靠上下文压力信号才触发恢复包。

## 交付与安装

本版本在本地形成完整可编辑的 Skill 文件包；若从 GitHub 克隆，在干净的仓库分支上应用更新文件并复核变更，再按需提交/推送。**文件包不是带 Git 历史的真实克隆**；本轮不会直接覆盖远端 `main`。

## 工作流开发与维护要求

后续维护必须保持 Skill 轻量，所有修改遵守以下要求：

1. **先审计，再修改。** 从真实用户问题或已验证需求出发；先检查现有核心规则、相关 reference 和脚本，定位根因，并确认现有规则是否已经覆盖。
2. **先分类，再决定放在哪里。** 必须长期生效、跨项目通用的规则放入 `SKILL.md`；详细过程放入按需加载的 `references/`；项目路径、结果、阈值和临时决策留在项目工作区或 handoff 中。不得把项目专属事实写进通用 Skill。
3. **采用最小充分修改。** 优先修改现有对应文件，不随意增加 Skill、reference、检查清单或脚本。只有形成独立、可复用能力时才新增组件。保留已验证功能，避免推测性功能、重复门禁和并行机制。
4. **保护执行效率。** 不增加逐轮阶段扫描、重复读取 reference、递归调用 Skill、轮次计数、强制记账或只有状态播报的步骤。复用当前会话已有信息，先完成任务，不能让流程检查反过来阻塞任务。
5. **验证受影响的行为。** 运行 Skill validator 和相关自测；针对变更路径增加定向回归测试，条件允许时使用真实代表性案例。测试实际打包文件及文档所述的导入/解压路径。需要确认身份时核对包内容和哈希。未验证持久化状态，不得把生成 ZIP 说成安装成功；未核实远端状态，不得声称仓库更新完成。
6. **让发布可追溯。** 源码、README、CHANGELOG 保持一致，保留上游来源和许可证边界。仓库变更使用范围明确的分支/PR，检查最终 diff，并在相关验证通过后再合并。同一发布中避免混入无关重构。
7. **重大工作后建立检查点。** 重大修改或有意义的阶段结束后，生成最小可恢复工作区 ZIP 和 `HANDOFF.md`。只有存在可靠运行时信号，或能确认发生上下文压缩/丢失时，才因上下文压力提前打包。下载链接放在正常三段式回复的第二段；独立实验完整证据链仅在用户明确要求时另行生成。
8. **停止低收益分支。** 未经真实任务验证有明确收益的实验性功能，不得进入核心 Skill。期刊写作风格指南和学科级绘图偏好指南试验分支已停止；未经用户明确要求，不得重新启动。

### 完成标准

只有在用户问题已解决、相关回归检查通过、安装包/远端状态得到如实核验，并且未完成工作可通过 handoff 恢复时，修改才算完成。达到这些条件后即停止，不再追加无必要的复审循环。
