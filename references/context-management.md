# Context Recovery and Continuity Pressure

Load only for new-session/workspace recovery, material state conflict/loss, major continuity transition, or a reliable runtime signal of compaction risk. Not an every-turn project-management loop.

## 1. Recover the minimum authoritative state

Read only what affects the active request:

- scientific question, current code/method and exact evaluation contract;
- authoritative version/configuration and current manuscript when relevant;
- data/splits/protocol, frozen candidate, final-test exposure and independent confirmation status;
- **when multiple branches matter:** active IDEA IDs/claim versions, parent relationships, current statuses, decisive supported/negative evidence, pending runs and next decisions;
- pending external task if any, and its identifier, output and status.

A new upload is not automatically the current authority. Resolve conflicts by provenance, source run and protocol applicability, not modification date alone. Archived rejected branches are not reopened without new distinguishing evidence or an explicit user request.

## 2. File priorities

- **P0:** current state/active IDEA index, executable code/config and current manuscript as needed;
- **P1:** frozen evidence/protocol and claim-to-evidence mapping;
- **P2:** development/diagnostic results and revision history;
- **P3:** historical/supporting records.

Read P0 first, then only what resolves the immediate task; do not reconstruct the entire dialogue or all dormant IDEA branches.

## 3. Pending external execution

Store sufficient identity to avoid duplicate dispatch: IDEA/claim version, run ID/purpose, code/config/data/seed, evidence class, expected result and status. A partial return supports provisional interpretation, not final multi-branch ranking. Do not relaunch an equivalent still-pending job.

## 4. Reliable pressure handling

Only use context pressure as a trigger when the runtime reliably signals it or earlier context was demonstrably lost. Never invent a remaining-token percentage. Finish the safe atomic operation, load `references/handoff-workspace.md`, record unfinished tasks and current branch map, package the minimum recoverable state and warn briefly. Stop a further long multi-step operation only if continued work materially risks losing authoritative state; otherwise continue. If pressure is not observable, use explicit handoffs or major checkpoints instead.

## 5. Handoff routing

Read `references/handoff-workspace.md` only when a handoff/export is explicitly requested, a meaningful major revision or phase close creates a new authoritative baseline, or the pressure rule above is met. Do not checkpoint every small patch or ordinary experimental result.
