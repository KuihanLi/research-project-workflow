# Research Project Workflow

> 中文说明 | [English](README.md)

Research Project Workflow 是一个面向长期科研项目的轻量级工作流 Skill。它不是替代模型、代码、实验平台或论文工具，而是负责让 ChatGPT 在“研究设计 → 代码实现 → 实验验证 → 证据判断 → 论文写作 → 项目交接”之间保持一致、可复现、不过度阻塞的推进逻辑。

## 这个 Skill 能干什么

它覆盖从研究想法到论文投稿的完整链路。

### 1. 研究设计

把模糊想法整理成可执行方案，包括：

- 研究问题与假设
- 方法目标与边界
- 实验冻结前的查新与 baseline 可行性验证
- baseline / control 设计
- 数据与评价指标
- 成功标准与停止条件
- 最小实验闭环

例如你说：

> “我有一个模块，想验证它是否真的能提升缺失时序预测。”

它不会只给一个宽泛建议，而会进一步整理成：比较对象、控制变量、实验矩阵、需要保留的证据，以及什么结果才足以支持论文 claim。

### 2. 方法设计与修改

帮助判断：

- 当前方法的创新点是否成立
- 现有结果是否支持继续改模型
- 性能问题来自表示、训练、数据、随机性还是假设本身
- 哪些改动属于真正的机制改进，哪些只是堆模块
- 是否已经达到应该冻结模型、停止调参的阶段

目标不是无限追求“再涨一点”，而是让每次修改都对应明确问题。

在正式展开主实验矩阵前，新版还要求先完成与核心 claim 成比例的查新，并至少验证最关键的可比 baseline 路径，避免实验完成后才发现创新性或比较基线发生根本变化。

### 3. 代码与实验

可以协助：

- 实现或修改实验代码
- 设计 smoke test
- 组织实验矩阵
- 规划 seed / 多次重复实验
- 设计消融实验
- 分析报错和失败原因
- 聚合多次运行结果
- 区分“代码失败”和“科学假设失败”

对于需要在服务器、GPU、硬件设备或外部环境执行的实验，它会先完成所有可以本地准备的代码、配置和命令，再给出尽量紧凑的可执行任务，而不是反复进行“一行修改 → 跑一次 → 再修改”的低效循环。

### 4. 实验纪律与证据管理

这是该 Skill 最重要的部分之一。

它会持续维护这些原则：

- train / validation 用于训练、调参和模型选择
- final test 用于冻结后的最终验证
- 不允许根据 final-test 结果继续调参
- development、mechanism / ablation、final evidence 分开解释
- 不隐藏负结果或更强的简单 baseline
- 当结果与假设冲突时，优先修改 claim，而不是回头污染测试集

换句话说，它不仅关注“结果好不好”，还关注这个结果是否真的能作为论文证据使用。

### 5. 结果分析与实验决策

例如你说：

> “这个模块提升不稳定，帮我判断下一步怎么实验。”

它会结合当前证据判断问题更可能来自：

- 随机性
- 训练不稳定
- baseline 过强或比较不公平
- 数据划分
- 表示机制
- 超参数敏感性
- 模块本身没有稳定贡献

然后优先给出**最小、最有区分度的一批实验**，而不是简单列出十几个“可以继续尝试”的方向。

### 6. 消融与机制验证

帮助设计真正能够回答科学问题的 ablation，例如：

- 去掉某模块后性能是否变化
- 模块是否只在特定数据分布下有效
- 改进来自参数量增加还是机制本身
- 方法是否改善目标机制，而不是偶然提高最终指标

重点不是“为了论文有一张消融表”，而是让消融实验能够支撑具体 claim。

### 7. 论文工作

可用于：

- Abstract
- Introduction
- Related Work
- Method
- Experimental Setup
- Results
- Discussion
- Conclusion
- Supplementary Material

同时会检查：

- claim 是否有对应证据
- novelty 表述是否超出实际贡献
- baseline 是否足够完整
- 负结果是否需要影响论文定位
- validation 发现和 final evidence 是否被混写
- 论文叙事是否与真实实验过程一致

### 8. 投稿与长期项目连续性

还可以处理：

- 在论文标题、摘要、贡献和章节框架锁定前，基于真实证据、官方 scope 与近期相关论文进行候选 venue 选优
- venue 定位
- 篇幅压缩
- 投稿材料准备
- 复现材料整理
- 新会话恢复项目状态
- 工作区交接
- 版本、实验记录和当前结论恢复

适合持续数周甚至数月的研究项目，而不是只解决单个问题。

## 这个版本特别强调什么

### Completion first：先完成任务

工作流不能成为任务本身的阻塞源。

只要当前任务可以正确完成，就直接完成。以下内容默认**不能**作为拖延交付的理由：

- 阶段标签
- handoff 是否最新
- 项目日志是否补齐
- 是否做了完整审计
- 是否完成了所有可选实验
- 是否更新了非关键元数据

只有以下情况才允许真正阻塞：

1. 会污染预留的 final test；
2. 会伪造实验、引用、文件或执行结果；
3. 存在安全、权限、破坏性或不可逆风险；
4. 缺少的信息会让结果实质错误，而且无法合理推断或标记为假设。

### Evidence discipline：证据边界优先

研究可以快，但不能靠破坏实验有效性来换速度。

该 Skill 会重点保护：

- validation / test 边界
- frozen method
- seed 语义
- baseline 公平性
- claim-evidence 对齐
- 实验 provenance

### Lazy loading：按需读取，而不是每轮重读

`SKILL.md` 是会话级常驻核心规则；`references/` 是过程说明，只在真正需要时加载。

| 当前任务 | 才读取 |
| --- | --- |
| 新研究想法、重大方法重构、实验前查新/基线验证、实验合同 | `references/idea-to-plan.md` |
| 实验实现、调试、运行、失败诊断、结果聚合 | `references/code-experiment-loop.md` |
| 论文、claim、框架设计前 venue 选优、投稿 | `references/paper-workflow.md` |
| 新会话恢复、工作区交接、上下文冲突 | `references/context-management.md` |

普通连续讨论不会因为再次使用该 Skill 就重新把所有文件读一遍。

### 三段式输出：复杂工作，简洁交付

默认用户可见回复压缩为：

1. **结论 / 本次完成**
2. **关键依据 / 交付**
3. **下一步**

内部分析可以复杂，但不会把大量流程说明、自检、路由过程和重复总结倾倒给用户。

## 最适合怎么用

它特别适合这些场景：

### 从想法开始

```text
使用 Research Project Workflow，把这个想法整理成最小可验证的研究方案，并给出 baseline、控制变量和成功标准。
```

### 模型已经在开发

```text
使用 Research Project Workflow，检查当前模型还有没有继续修改的必要，并给出最小下一轮实验。
```

### 多次实验已经返回

```text
根据刚跑完的 5 seeds 结果，判断方法是否稳定、是否应该冻结，以及哪些 claim 现在已经有证据支持。
```

### 准备写论文

```text
现在进入论文阶段，使用 Research Project Workflow，把现有结果整理成 Results + Discussion，并检查 claim-evidence 是否一致。
```

### 新会话继续长期项目

```text
使用 Research Project Workflow 恢复上次项目状态，从最新有效实验继续，不要重新从头设计。
```

## 它不是什么

它不是：

- 自动替代研究者做所有科学判断的系统
- 自动运行外部服务器或硬件实验的工具
- 为了流程完整而强制执行所有步骤的“项目管理器”
- 保证任何模型都能提升性能的调参器

它更像是一个**科研项目控制层**：让 ChatGPT 在方法、代码、实验、证据和论文之间保持同一套逻辑，同时减少长项目中常见的重复分析、test 泄漏、无限调参、上下文丢失和工作流自我膨胀。

## 安装 / 迁移

克隆或下载本仓库，并保持目录结构不变。

如果你的 ChatGPT 环境支持自定义 Skill 导入，可以按照对应环境的 Skill 打包流程，将仓库内容打包后导入。

不要把 `references/`、`agents/` 或 `assets/` 扁平化，因为 `SKILL.md` 直接引用这些路径。
